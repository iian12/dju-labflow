# LabFlow 구현 점검 및 개선 제안

점검일: 2026-11-20 (Asia/Seoul)

> 초기 점검 시점의 기록입니다. 이후 Heartbeat 연결 상태·수동 종료, ADMIN API 테스트의 Studio 통합, 이전 디자인 앱 제거를 구현했습니다. 아래의 미구현·검사 실패 내용은 초기 상태를 설명합니다. API 카탈로그 검사와 SDK 포맷 위반도 후속 작업에서 해결했으며 최신 사용법은 [관리자 API 테스트 안내](admin-api-workbench.md)를 참고하세요.

## 현재 상태

개인 사용자의 실험 추적 MVP에 필요한 핵심 흐름은 연결되어 있다. 회원가입 → 이메일 인증 → 로그인 → 프로젝트 생성 → API 키 발급 → Python SDK 기록 → 웹 조회·비교 → Artifact 다운로드까지 구현되어 있다.

다음 개발에서는 기능 수를 늘리기 전에 **조회 비용, 파일 업로드와 기록 간 잠금, 비정상 종료 식별, 운영 스키마 관리**를 먼저 보완하는 것이 좋다.

검토 대상은 활성 앱 `frontend`, Spring 백엔드, Python SDK, 별도 `frontend-design`과 `sdk_test`, SQL 및 실행 스크립트다. 저장소 코드와 격리된 테스트 환경을 기준으로 점검했다. 운영 MariaDB, 실제 SMTP, 외부 서비스의 배포 설정은 검증하지 않았다. 제품 소스는 수정하지 않았다.

## 우선 개선할 사항

P1은 운영 전 또는 다음 개발 주기에 우선 처리할 항목이고, P2는 사용성·유지보수·기능 확장 항목이다. 아래 영향 중 부하와 장애 시나리오는 코드 구조에서 도출한 것이며 부하 테스트로 측정한 수치는 아니다.

### 1. P1 — Run 전체 재조회 구조 개선

- 근거: `frontend/src/ProjectWorkspace.tsx:24`에서 Run의 모든 페이지를 읽고, 100개씩 나누어 요약도 순차 조회한다. 이 작업을 5초마다 반복하며 설정·상세 화면에서도 상위 컴포넌트가 계속 실행한다.
- 영향: Run 10,000개이면 한 번 갱신할 때 목록 약 100회와 요약 약 100회의 HTTP 요청이 필요하다. 검색·정렬도 전체 데이터를 받은 뒤 브라우저에서 수행한다. 페이지별 상태 집계와 지표 최신값 계산도 반복된다.
- 제안: 서버 검색·상태 필터·정렬을 추가하고 화면의 한 페이지와 해당 요약만 조회한다. 프로젝트 집계는 별도 조회하고, 상세·설정에서는 전체 목록 폴링을 중단한다. 완료된 Run의 갱신도 종료한다.
- 완료 기준: Run 개수가 늘어도 한 페이지를 여는 요청 수가 일정하며, 대량 데이터에서도 검색·정렬이 서버 기준으로 동작한다.

### 2. P1 — 파일 전송과 DB 잠금 분리

- 근거: `backend/src/main/java/com/dju/labflow/run/artifact/application/LocalArtifactService.java:53`의 트랜잭션 안에서 프로젝트·Run을 잠근 뒤 입력 스트림 전체를 복사한다. `RunAccessPolicy.requireOwnedForUpdate()`와 `SdkRequestService.execute()`도 같은 프로젝트 행을 잠근다.
- 영향: 큰 파일이나 느린 업로드가 진행되는 동안 같은 프로젝트의 다른 Run에서 지표·로그·Heartbeat를 기록하는 요청도 대기할 수 있다. 일반 기록 요청도 프로젝트 단위로 직렬화된다.
- 제안: 짧은 트랜잭션으로 업로드 예약·용량을 확보하고, 파일 전송은 DB 잠금 밖에서 수행한 뒤 짧게 완료 처리한다. 실패·삭제 경합을 처리하는 상태 전이와 임시 파일 정리가 필요하다. 트래픽 증가 시 Run별 쓰기 잠금과 프로젝트 삭제 조정 방식도 재설계한다.
- 완료 기준: 파일 업로드 중 같은 프로젝트의 다른 Run에서 기록과 Heartbeat가 정상 응답하며, 용량 초과·프로젝트 삭제·전송 실패에도 고아 데이터가 남지 않는다.

### 3. P1 — Heartbeat를 실제 장애 식별에 사용

- 근거: Run 상태는 `RUNNING`, `COMPLETED`, `FAILED`뿐이다. Heartbeat는 저장하고 환경 탭에 표시하지만 미수신을 감지하는 스케줄러나 상태 판단은 없다.
- 영향: 강제 종료, 머신 장애, 프로세스 종료로 종료 API를 호출하지 못하면 계속 진행 중으로 표시된다.
- 제안: 먼저 `연결 끊김/확인 필요` 표시와 마지막 수신 시각을 목록·상세에 노출한다. Heartbeat 미사용 클라이언트를 구분하고, 유예 기간·재연결 정책을 정한다. 이후 소유자의 종료 처리나 복구 흐름을 추가한다.
- 완료 기준: 정상 실행, 일시적 네트워크 단절, 강제 종료, Heartbeat 비활성화가 구분된다. 원격 학습 프로세스 취소는 별도 에이전트·통신 구현이 필요하다.

### 4. P1 — 운영 DB 마이그레이션과 MariaDB 검증

- 근거: 공통 설정의 `spring.jpa.hibernate.ddl-auto=update`를 prod에서도 상속한다. DB 변경 SQL은 별도 파일이고 Flyway/Liquibase 적용 및 MariaDB 기반 자동 테스트는 없다.
- 영향: 배포 시 변경 순서와 적용 이력 관리가 어렵다. H2 통과만으로 MariaDB의 행 잠금·네이티브 SQL·컬럼 동작까지 확인할 수 없다.
- 제안: 버전별 마이그레이션을 도입하고 prod에서는 스키마 검증으로 전환한다. MariaDB 컨테이너 테스트로 동시 기록·삭제·키 폐기·refresh 회전·시계열 SQL을 확인한다.
- 완료 기준: 빈 DB 설치와 이전 버전 DB 업그레이드가 자동 재현되고, 실제 MariaDB에서 핵심 경합 테스트가 통과한다.

### 5. P1 — 프록시 환경의 요청 제한과 로그인 보호

- 근거: 인증 코드 요청 제한은 `request.getRemoteAddr()` 기준의 JVM 메모리 캐시다. 게이트웨이는 `X-Forwarded-For`를 보내지만 저장소의 Spring 설정에는 전달 헤더 처리 구성이 없다. 로그인에는 별도 요청 제한이 보이지 않는다.
- 영향: 현재 설정대로 로컬 게이트웨이를 경유하면 실제 사용자들이 프록시 IP의 시간당 발송 제한을 공유할 수 있다. 여러 백엔드 인스턴스에서는 제한 카운터가 분리된다.
- 제안: 신뢰하는 프록시 경계를 명시한 뒤 실제 클라이언트 IP를 안전하게 복원한다. 로그인도 계정·IP 조합으로 속도를 제한한다. 다중 인스턴스 운영 시 공용 저장소나 게이트웨이에서 일관된 제한을 적용한다.
- 완료 기준: 서로 다른 사용자 IP의 제한이 분리되고, 임의 전달 헤더로 우회할 수 없으며, 로그인 반복 실패도 제한된다.

### 6. P1 — SDK 전송 장애와 종료 대기 개선

- 근거: 명시적 지표·로그 전송은 동기 HTTP이고 기본 `max_retries=0`이다. 자동 출력은 1,000개 큐가 가득 차면 드롭하며, 종료에서는 큐를 비울 때까지 `thread.join()`에 시간 제한 없이 대기한다.
- 영향: 서버 장애가 학습 코드에 예외를 전파하거나, 로그가 많은 상태에서 종료를 오래 지연시킬 수 있다. 현재는 전송 실패 기록의 디스크 보관·재전송 기능이 없다.
- 제안: 엄격한 오류 전파 모드는 유지하면서 선택형 비동기 배치·로컬 보관·재전송 모드를 제공한다. flush 종료 기한, 미전송 개수, 드롭 수를 명확하게 노출한다. 재전송에는 기존 요청 ID를 유지한다.
- 완료 기준: 백엔드 장기 장애 중 동작과 종료 대기 시간이 설정 가능하고, 복구 후 중복 없이 기록을 재전송한다.

## 코드·문서·개발 환경 정리

1. **자동 검증 연결:** 저장소에 GitHub Actions 등 CI 설정이 없다. 현재 있는 백엔드·SDK·프런트 검증을 PR 필수 검사로 연결한다. 실제 HTTP/브라우저 통합 테스트는 환경변수 미설정 시 건너뛰므로 별도 job에서 명시적으로 활성화한다.
2. **기준 프런트 명확화:** 실제 진입점은 `frontend/src/main.tsx`의 `StudioApp`이다. 이전 App·샘플 데이터·디자인 테스트와 별도 `frontend-design`의 유지 목적을 정하고 보존 또는 제거한다. 디자인 변경의 회귀 검사를 활성 Studio 대상으로 옮긴다.
3. **오래된 API 도구 갱신:** `frontend-design/src/apiCatalog.ts`와 대응 테스트가 최신 컨트롤러를 따라가지 못한다. OpenAPI에서 생성하거나, 도구의 지원 범위를 명시한다.
4. **문서 최신화:** `frontend-design/README.md`는 키 목록·폐기 API가 없다고 설명하지만 현재 백엔드에는 있다. `sdk_test`는 0.1.1 커밋, 현재 SDK는 0.3.0이다. `test` 브랜치 관련 설명도 현재 CONTRIBUTING의 main/develop 정책과 맞춰야 한다.
5. **루트 실행 안내:** 루트 README에 구성도, 기준 앱, 포트, Java·Node·Python 요구사항, 환경 설정, 시작 순서, 테스트와 배포 절차를 모은다.
6. **배포 재현성과 관측:** 저장소에는 Docker/Compose 및 배포 파이프라인이 없다. 기동·헬스체크·백업·복원 절차, DB/파일 저장소의 일관된 백업, 요청 추적과 실패율·지연·디스크 사용량 관측을 구성한다. Actuator 의존성은 있으나 운영 readiness 접근 정책은 별도 확인이 필요하다.
7. **보관 데이터 정리:** SDK 요청 멱등성 이력, 만료·폐기 refresh 토큰, 미인증 계정·인증 코드의 보관 기간과 정리 작업을 정의한다. 현재 refresh 만료 삭제 저장소 메서드는 있지만 실행하는 주기 작업은 없다. 멱등성 이력 삭제에는 보장할 재전송 기간을 먼저 정해야 한다.
8. **스타일 일관성:** 프런트의 긴 단일 행 JSX를 읽기 쉬운 컴포넌트로 나누고 lint/format 명령을 실제 의존성과 연결한다. SDK의 포맷 위반 1곳도 정리한다.
